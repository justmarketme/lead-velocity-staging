# platform-architect — P2-SCHEMA summary (written by the orchestrator; the harness does not let sub-agents write report files)

Five additive, idempotent Supabase migrations (`supabase/migrations/20261002_smc_01…05`) plus a guarded synthetic seed (`supabase/seed/smc_synthetic.sql`, aborts unless `smc.allow_synthetic=on`) implement the crm-gap map without forking the CRM. Migration 01 holds the NH-15 security fixes — including a new finding S10: two live policies let any signed-in broker read every lead and message — and is marked APPLY ONLY AFTER NH-15 YES. The rest add 28 tables (21 `public`, 7 `ops`), extend 10 existing tables, expose the prompt's names as views over existing tables (`conversations`, `bookings`, `reports`, `v_cycle_progress`), build a pseudonymised `facts` layer of nine fact views plus `v_watchlist`, and an append-only PII-redacted `audit_log` fed by a trigger on every SortMyCover write. Disposition codes follow 4.12a (`fit_*`/`nofit_*`; the gap map's `good_fit_*` was corrected by the orchestrator). The agent applied every file twice on a local Postgres 16 with a Supabase stub after replaying the 60 repo migrations, and ran access tests (broker isolation, anon denied, `n8n_app` least privilege, `facts_reader`), the double-booking rule and the watchlist. Nothing touched the live project. `schema.md` (Mermaid ERD, mapping, write contract) and `security-runbook.md` (apply order, non-SQL fixes, role logins) are in this folder.
