## I-33a / I-30e (2026-10-02)
The billing workflows no longer read or write Supabase Vault directly. W16 saves the card token and the plan subscription through `smc_vault_store_paystack_auth` / `smc_vault_store_paystack_sub`, and W19's cycle-end charge reads the token only through `smc_vault_paystack_auth_code(broker_id)`, which returns nothing unless the broker has opted in to card auto-renew. A grep for `vault.` across W16–W19/W25 is empty. W19 now has the portal's `POST /billing-autorenew` endpoint: the broker's Supabase JWT is checked the same way as on `/slots` (`verifySupabaseJwt` from automation/security/lead-token.js), the broker is taken from the token (never from the request), and auto-renew is switched off in one guarded update plus one timeline row (double tap does nothing), then a WhatsApp confirmation and a W22 `card_autorenew_off` notice go out. The endpoint can only switch off; switching on stays an opt-in at card checkout (`{on:true}` → 400). No card data is stored. Tests: 47/47 offline (`billing.test.js` 28, `autorenew.test.js` 11, `fais-boundary` 3, W16–W19/W25 wrappers 5). Orchestrator re-ran the suite and the vault grep.
**needs_human / owner:** the billing credential "Supabase CRM (Postgres, billing role)" must connect with `n8n_app`'s rights or the wrappers fail with permission denied (devops-security); Paystack Plan-mode auto-renew is not stopped by our flag — W19 sends a W22 notice for Jonathan to disable the plan in the dashboard until `smc_vault_paystack_sub_token(broker_id)` exists (migration 10/11); confirmation currently reuses `broker_onb_next` — a dedicated `broker_autorenew_off` template should be drafted before GATE-TEMPLATES.
