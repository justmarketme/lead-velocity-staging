# W22 Alerts: thresholds, rules and contracts

**Owner:** devops-security · **Workflow:** `automation/W22.json` (n8n, import inactive) · **Test:** `node --test automation/tests/W22.test.mjs`
**Reads:** `ops.w22_metrics` (view), `ops.notifications`, `brands.booking_ui` · **Writes:** `ops.notifications`, `brands.booking_ui` (Flow revert only) · **Sends:** WhatsApp `ops_alert` (utility template, to our own two numbers), Graph `sendMail` copy to howzit@, Twilio voice (4 h escalation only).

W22 is the single place that decides *whether, when and to whom* an alert goes. Other workflows never message Jonathan/KG directly for alerts. They hand W22 a signal (section 3), and W22 applies the same dedupe, DND and escalation to all of them (6.8b: "one place to look, one message to read, nothing twice").

**Recipients (I-38b):** every row carries `"to"` (default `jonathan,kg`). The W34 `dsar_*` kinds go to the Information Officer, `W34_IO_RECIPIENT` (`jonathan` or `kg`; anything else falls back to `jonathan`), except `dsar_overdue` (both). A held-in-DND row is released to its stored `"to"`. Escalation of a red row still goes to the other partner (2 h) and both (4 h).

**Amber** never sends a WhatsApp, except a registered `notify_now` kind (only `dsar_received`), which goes to its recipient at once (DND still holds it to 07:00) and never escalates. It is written to `ops.notifications` with `status = 'amber_to_pulse'`, and W32 folds it into the 07:00 pulse (6.8b "alerts are rare and actionable; the daily pulse is the routine"). **Red** sends WhatsApp `ops_alert` to both partners, an email copy to howzit@, and puts the console banner up (an open red row).

## 2. Delivery rules (6.8b)

| Rule | Implementation (node) |
|---|---|
| **Dedupe:** the same signal never notifies twice in 24 h | `dedupe_key = signal_key|scope|severity`. One atomic SQL statement (**Dedupe 24 h + write ops.notifications**) inserts only if no row with that key was created in the last 24 h (`send_failed` rows don't count). Otherwise it bumps `last_seen_at` / `seen_count` on the existing row. An amber → red change is a new key, so it is allowed through. |
| **DND 22:00–07:00 SAST** except the always-send set | **Policy** node. SAST = UTC+2 with no DST. Red signals outside the always-send set are stored as `held_dnd`. **Escalation policy** releases them on the first 5-min tick at or after 07:00, so they arrive at 07:00–07:05. Always-send set: `guardrail_trip`, `waba_restriction`, `failed_debit`, `uptime_down` (api), `vps_down`. |
| **Escalation:** unacknowledged red at 2 h → the other partner; at 4 h → Twilio voice call | **Due escalations** (SQL) + **Escalation policy**. Level 0 → 1 at 2 h after `first_sent_at`: re-send `ops_alert` (prefixed "ESCALATED, unacknowledged 2 h") to the partner who is *not* primary for that kind (6.8a duty table: KG is primary for payments and disputes, Jonathan for everything else). Level 1 → 2 at 4 h: Twilio voice call to both numbers (the TwiML `<Say>` holds no lead data). Escalations of non-always-send items pause during DND. Always-send items escalate through the night. |
| **Acknowledge** | Console banner "Acknowledge" sets `acked_at`/`acked_by` on the row. Any workflow can also call W22 with `{"type":"ack","notification_id":"…","acked_by":"jonathan"}`, for example W07 when a partner replies "ACK" to the alert. |
| **Stuck console approvals** (I-36b) | **Re-queue stuck approvals** (SQL, on the 5-min sweep) + **Judge stuck approvals**. Rows `kind='approval'` in `sending` with `updated_at` older than 10 min (W32 claimed them, then crashed or n8n restarted) go back to `queued` with `attempts + 1` (`FOR UPDATE SKIP LOCKED`, so W32's 1-min claim and W22 never fight). After 3 re-queues the row becomes `send_failed`. One `approval_stuck` signal per sweep: amber when everything was re-queued, red when one gave up. `attempts` is `payload.requeue_attempts` until `ops.notifications` gets an `attempts` column (needs_human, platform-architect). |
| **Within 1 h of the trigger** | 5-min sweep + event path. Worst case is 5 min for metric signals and 1 h for hourly probes. |
| **No PII in alerts** | `what`, `impact` and `first_action` pass through `redact.js` (numbers, emails and SA IDs masked). Scopes carry ids (`campaign:…`, `broker:…`), never lead names. The `payload` column stores the redacted signal. |

## 3. Producer contract (how other workflows raise an alert)

Call W22 with **Execute Workflow** (source: database, workflow W22, mode "run once with all items"), one item per signal:

```json
{"signal_key":"fsca_mismatch","scope":"broker:brk_mark","severity":"red",
 "what":"FSP 00000 not found on FSCA register","impact":"Go-live blocked for this broker",
 "first_action":"Check the FSP number with the broker","since":"2026-10-02T09:14:00Z","source":"W20"}
```
- `severity` is `red` or `amber`, default red. `always_send: true` is honoured but should be rare. The policy list in section 2 is the norm.
- Raw objects are also accepted and mapped: a WhatsApp change object (`{"field":"message_template_status_update","value":{…}}`, `phone_number_quality_update`, `account_update`), forwarded by the WhatsApp ingress after signature verification, and a Paystack event body (`invoice.payment_failed`, `charge.failed`, `subscription.not_renew`), forwarded by W16/W19 after signature verification.
- Anything W22 cannot read becomes an amber `unknown_signal`, so nothing is silently dropped.
- **Uptime monitor callback:** `POST {api}/webhook/w22/uptime` with header auth (credential *W22 uptime monitor header token*) and body `{"monitor":"api.leadvelocity.co.za","state":"down|up","since":"…","duration":"…"}`. See `vps/UPTIME.md`.

## 4. `ops.w22_metrics`, the view W22 reads (contract for platform-architect)

One row per metric per scope: `metric text, scope text, value numeric, n numeric, context jsonb, since timestamptz`. A null `value` is skipped.

| metric | scope | value | n / context |
|---|---|---|---|
| `raw_cpl_zar` | `campaign:{id}` | spend ÷ raw leads, cycle to date | `context.spend_zar` |
| `qualify_rate` | `campaign:{id}` | qualified ÷ raw (0–1) | `context.spend_zar` |
| `cost_per_qualified_zar` | `campaign:{id}` | spend ÷ verified qualified (3.3) | `context.days_live` |
| `show_rate_14d` | `broker:{id}` and `global` | attended ÷ (attended + no_show), outcomes in last 14 d | `n` = outcomes |
| `first_message_sla_breaches` | `global` | leads created in the last 15 min whose first WhatsApp `sent_at − created_at > 60 s` (or still unsent after 60 s) | `context.worst_seconds` |
| `leads_last_hour` | `global` | leads created in the last 60 min | `context.baseline_hourly_median_7d` |
| `oauth_refresh_failures_24h` | `broker:{id}` | failed refreshes in 24 h | — |
| `secret_days_to_expiry` | `secret:{name}` | days until `ops.secret_inventory.expires_at` | — |
| `backup_hours_since_success` | `global` | hours since the last `ok` `pg_dump` in `ops.backup_runs` (9999 if none) | — |
| `restore_test_days_since` | `global` | days since the last `ok` `restore_test` (9999 if none) | — |

The last three come from tables defined below, so their view SQL is given here. The funnel metrics come from `facts.*` / `ad_metrics`, and platform-architect writes those `UNION ALL` branches when the facts layer lands (crm-gap §A5, 6A2).

```sql
-- W22 ops DDL (proposed for platform-architect's ops-schema migration, NH-16). W22.test.mjs runs this block on a scratch Postgres.
CREATE SCHEMA IF NOT EXISTS ops;

CREATE TABLE IF NOT EXISTS ops.notifications (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind             text NOT NULL DEFAULT 'alert',
  "to"             text NOT NULL,
  dedupe_key       text NOT NULL,
  signal_key       text NOT NULL,
  scope            text NOT NULL DEFAULT 'global',
  severity         text NOT NULL CHECK (severity IN ('red', 'amber')),
  always_send      boolean NOT NULL DEFAULT false,
  status           text NOT NULL CHECK (status IN ('sending', 'held_dnd', 'amber_to_pulse', 'sent', 'escalated', 'send_failed', 'cancelled', 'queued', 'acked')),  -- queued/acked: W32 console approvals (migration 06)
  source           text,
  what             text,
  impact           text,
  first_action     text,
  since_label      text,
  primary_partner  text NOT NULL DEFAULT 'jonathan' CHECK (primary_partner IN ('jonathan', 'kg')),
  payload          jsonb NOT NULL DEFAULT '{}'::jsonb,
  channel_log      jsonb NOT NULL DEFAULT '[]'::jsonb,
  escalation_level smallint NOT NULL DEFAULT 0,
  created_at       timestamptz NOT NULL DEFAULT now(),
  first_sent_at    timestamptz,
  sent_at          timestamptz,
  acked_at         timestamptz,
  acked_by         text,
  last_seen_at     timestamptz,
  seen_count       integer NOT NULL DEFAULT 1,
  updated_at       timestamptz NOT NULL DEFAULT now()   -- migration 03; W32 sets it on claim, W22 times 'sending' from it
);
CREATE INDEX IF NOT EXISTS notifications_dedupe_idx ON ops.notifications (dedupe_key, created_at DESC);
CREATE INDEX IF NOT EXISTS notifications_open_red_idx ON ops.notifications (first_sent_at) WHERE severity = 'red' AND acked_at IS NULL;

-- Metadata only: never the secret value.
CREATE TABLE IF NOT EXISTS ops.secret_inventory (
  name              text PRIMARY KEY,
  holder            text NOT NULL,
  stored_in         text NOT NULL,
  rotate_every_days integer NOT NULL,
  rotated_at        timestamptz,
  expires_at        timestamptz,
  owner             text NOT NULL DEFAULT 'devops-security'
);

CREATE TABLE IF NOT EXISTS ops.backup_runs (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind        text NOT NULL CHECK (kind IN ('pg_dump', 'n8n_export', 'restore_test')),
  started_at  timestamptz NOT NULL,
  finished_at timestamptz,
  ok          boolean NOT NULL,
  bytes       bigint,
  sha256      text,
  location    text,
  note        text
);

CREATE OR REPLACE VIEW ops.w22_metrics AS
SELECT 'backup_hours_since_success'::text AS metric, 'global'::text AS scope,
       COALESCE(EXTRACT(epoch FROM now() - max(finished_at)) / 3600, 9999)::numeric AS value,
       0::numeric AS n, '{}'::jsonb AS context, max(finished_at) AS since
  FROM ops.backup_runs WHERE kind = 'pg_dump' AND ok
UNION ALL
SELECT 'restore_test_days_since', 'global',
       COALESCE(EXTRACT(epoch FROM now() - max(finished_at)) / 86400, 9999)::numeric, 0, '{}'::jsonb, max(finished_at)
  FROM ops.backup_runs WHERE kind = 'restore_test' AND ok
UNION ALL
SELECT 'secret_days_to_expiry', 'secret:' || name,
       (EXTRACT(epoch FROM expires_at - now()) / 86400)::numeric, 0, '{}'::jsonb, now()
  FROM ops.secret_inventory WHERE expires_at IS NOT NULL;
-- platform-architect: UNION ALL the funnel metrics (raw_cpl_zar … oauth_refresh_failures_24h) from facts.* here.

-- Least privilege for the n8n role (NH-09): read the view, write notifications, nothing else in ops.
```

## 5. Configuration (names only; values in `.env` / n8n credentials)

- **Env read by W22:** `NODE_ENV`, `META_GRAPH_VERSION`, `PHONE_NUMBER_ID`, `WHATSAPP_TEST_PHONE_NUMBER_ID`, `OPS_WHATSAPP_JONATHAN`, `OPS_WHATSAPP_KG`, `OPS_EMAIL`, `HOWZIT_MAILBOX`, `CONSOLE_URL`, `PORTAL_URL`, `CONSUMER_DOMAIN`, `N8N_PUBLIC_URL`, `FLOW_ENDPOINT_URL`, `FLOW_PUBLIC_KEY`, `META_APP_SECRET` (signs the ping), `TWILIO_ACCOUNT_SID`, `TWILIO_VOICE_FROM`. n8n needs `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` and `NODE_FUNCTION_ALLOW_BUILTIN=crypto` (see SECURITY.md §2).
- **Credentials, referenced by name only.** On import, pick the matching credential in each node:
  - `LV Supabase - n8n_app (least privilege)` (Postgres)
  - `Meta system user token (Bearer)` (Header Auth: `Authorization: Bearer …`)
  - `MS Graph app-only - howzit@ Mail.Send` (OAuth2, client credentials)
  - `Twilio API key (Basic)` (Basic Auth: API key SID / secret)
  - `W22 uptime monitor header token` (Header Auth)
- **Workflow settings:** timezone Africa/Johannesburg. Successful executions are **not saved**, so alert payloads don't pile up in n8n execution data. Errors are saved and pruned per `EXECUTIONS_DATA_MAX_AGE`.
- **Every other workflow** sets *Settings → Error workflow = W22 Alerts*. That is how `workflow_failed` works.

## 6. Tests and the Section 7 drill

- `node --test automation/tests/W22.test.mjs` runs offline. It checks: the JSON structure, that there are no secrets, that every connection resolves, and that every credential is referenced by name only. It runs each Code node from the exported JSON in a sandbox: the thresholds, normalisation, DND hold/release, the always-send exceptions, the 2 h / 4 h escalation, recipient fan-out, and the encrypted Flow ping round trip against a simulated Meta-format endpoint. If Postgres 16 binaries exist on the machine, it also starts a throwaway cluster and runs the section 4 DDL, the dedupe SQL, the delivery-log SQL and the escalation query for real. Otherwise those cases are skipped.
- **Section 7 "DND + dedupe + escalation tested with synthetic alerts"** on the local n8n, with test numbers only:
  1. Run W22 *Execute Workflow* with a `fsca_mismatch` signal at 10:00. Expect 2 WhatsApps + 1 email.
  2. Run it again. Expect nothing (`seen_count = 2`).
  3. Set the row's `first_sent_at` back 2 h. KG gets the ESCALATED copy.
  4. Set it back 4 h. Both phones ring.
  5. Raise a non-always-send red at 23:00 (or set the machine clock). It is held, then released at 07:00.
  6. Raise `guardrail_trip` at 23:00. It sends at once.

## 7. Interpretations (flagged `needs_human` in the SUMMARY, with these defaults in place)

1. 6.8b says red goes "to both", then "at 2 h → re-send to the other partner". The default: both at T0. At 2 h, the re-send goes to the non-primary partner per 6.8a. At 4 h, a voice call goes to both.
2. 6.8a says "everything else in one 07:30 digest". 6.8b has the 07:00 pulse. The default: amber goes into the 07:00 pulse (W32), and held reds release at 07:00. There is no separate 07:30 digest.
3. W34 says "breach → both phones + email immediately", but the 6.8b DND exception list does not include a POPIA breach. The default is the strict 6.8b list: a breach declared at night arrives at 07:00. Adding `popia_breach` to the always-send set is a one-line change in the Policy node.
