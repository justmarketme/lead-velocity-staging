# W26 Go-live runner: the one human gate, then a script

**Trigger:** W16 confirms the **first successful payment** for a broker whose status is `onboarded` (6.6, 4.6 W26).
**Target:** under **60 minutes** from VPS purchase to `ready_for_go_live`, with the purchase as the only manual step. Until then, the local n8n + tunnel keeps handling traffic (`local/LOCAL-STAGING.md`), so nothing is lost in the gap.
**Rule:** any step that fails → halt, alert with the failing step, **nothing is unpaused**. Going live is a separate tap by Jonathan in the console (Section 7 "The button").

## Step 1: HUMAN GATE `GATE-VPS` (card payment: Jonathan only, 2.2 "never enter payment card details")
W26 sends Jonathan **one WhatsApp** (`ops_gate`): *"Gate waiting: **Buy the VPS**. Mark has paid. Default if nothing is done: leads keep running on the laptop. Tap below to review."* The button opens the console gate page, which carries:
1. **Link:** Hostinger hPanel → VPS → *Ubuntu 24.04 with n8n* template, **KVM 2**, **monthly** billing (6.6). *The KVM 2 price and template availability are checked once at purchase, per 4.0a ("devops-security, W26, at purchase"). The ≈ $8.99/month figure is the 24-month promo; monthly billing costs more. Jonathan sees the real price in hPanel before paying.*
2. **At checkout:** paste the **SSH public key** shown on the gate page (the laptop's `VPS_SSH_KEY_PATH.pub`) and set no root password login. Location: the nearest EU/Africa data centre hPanel offers. **Daily backups add-on: no.** Our own nightly encrypted off-server dump covers it (BACKUP.md) for R0.
3. **When the VPS shows an IP:** paste the IP into the gate page (or reply with it on WhatsApp). That sets `VPS_HOST` in the laptop `.env` and starts step 2.

Everything below is scripted.

**Publish targets and checksum (step 7, I-52c / I-53h).** n8n 2.x refuses to call an unpublished sub-workflow, so after the credential check, still with n8n stopped, step 7 runs `n8n publish:workflow --id=<id>` for every Execute Workflow target (`node automation/local/pubcheck.mjs --targets` lists them; 24 ids). **Publishing a target also starts its cron triggers.** Today that is W08, W09, W10, W12, W13, W20, W22, W29, W32, W35 (18 schedule triggers). On the VPS that is intended (they are the production reminders and sweeps, and the go-live gate is the campaign unpause, not the crons). On the laptop and on staging keep `DRY_RUN_SENDS=true` and the fail-closed env (RUN-LOCAL-NO-DOCKER.md section 2) so a started cron cannot send. Targets that carry webhook triggers (for example W03, W16) also go live on publish. After the start, step 7 exports the published graph from n8n's DB and runs `pubcheck.mjs --check`: it compares a stable hash of nodes + connections per workflow against the repo and halts on any MISSING or DRIFT line. Fix by re-import (`pubcheck.mjs --plan` prints the order: import everything, publish targets, restart) and `provision.sh --apply --from 7 --force-n8n-restore`. *ASSUMPTION: the published graph is read from `workflow_history` through `workflow_entity."activeVersionId"` (n8n 2.41.6); verify the query once on the laptop.*

**Restore checks (step 7, before activation).** The workflows come back with the active flags they had on the laptop, so n8n activates them as soon as it starts. That is why the credential check runs between the restore and `$DC start n8n`. On a miss it prints `MISSING credential: <type> "<name>" (blocks Wnn, …)` and the step halts with n8n stopped. Create the credential in the **laptop** n8n UI from `.env` (`local/CREDENTIALS.md` table B says what backs each one), then run `provision.sh --apply --from 7` (no `07.done` marker was written, so the restore runs again and streams the laptop DB with the new credential; on the `N8N_BACKUP_FILE` path, take a fresh backup first). Before W26, run the same check on the laptop (CREDENTIALS.md, top). OAuth2 credentials must also be *connected*, which the check cannot see: open each `microsoftOutlookOAuth2Api` / `oAuth2Api` credential once in the editor after step 9.

**On failure:** the script prints `HALT at step N` and posts `{step, ok:false}` (signed) to the local n8n's `/webhook/w26/status`. W26 forwards that to W22 as a red `workflow_failed` with the step name. Resume with `provision.sh --apply --from N`. Rollback is unnecessary: the laptop stack is untouched and still live until step 11 re-points the webhooks. If step 11 has run and a later step fails, re-run step 11 with `N8N_PUBLIC_URL` set to the tunnel (or just fix forward).

**After step 15 (ready):** the laptop keeper (`local-tick.ps1`) can be disabled. The laptop n8n must **not** keep processing. Deactivate its workflows so leads are never handled twice. Before that, the 6B.10 rehearsal (Jonathan as the lead, KG as the broker) runs on the production URLs.

## W26 workflow contract (for automation-engineer, who builds the n8n side)
- `POST /webhook/w26/status`: verify `X-LV-Signature = sha256=HMAC_SHA256(INTERNAL_HMAC_SECRET, "{X-LV-Timestamp}.{body}")` with a 5-min replay window (`verify-webhooks.js`: `timingSafeEqualStr` + `checkReplayWindow`). Then `ok:false` → W22 signal. `ok:true` with `name = "ready"` (step 15; key on the name, not the number) → set the broker ready + `ops_gate`.
- W26 never calls the Meta budget API. Unpausing happens only on Jonathan's **Go live** tap.
